# 첨삭 신청

구글시트를 그대로 원본으로 두면서, 선착순 신청만 웹으로 받는 시스템.

기존 방식(시트 링크를 공유하고 학생이 직접 빈칸에 이름 입력)은 동시에 입력하면
나중 사람이 앞사람을 덮어쓴다. 구글시트에는 "먼저 쓴 사람이 이긴다"를 판정하는
단계 자체가 없기 때문이다. 이 프로젝트는 그 판정을 서버로 옮긴다.

```
브라우저 ──▶ Next.js (Vercel) ──▶ Apps Script ──▶ 구글시트
            페이지 + API 프록시    락 + 선점 판정     원본 유지
```

- 학생은 시트에 접근하지 않는다 → 남의 이름을 덮어쓰거나 지우는 것이 **불가능**
- 신청 즉시 성공/마감이 확정된다 → 관리자 확인을 기다릴 필요가 없음
- 결과는 지금 쓰던 시트의 그 칸에 그대로 쌓인다 → 관리자가 보는 화면은 그대로

---

## 왜 이 구조인가

**Apps Script 를 끼우는 이유.** Google Sheets API 에는 "비어 있으면 쓴다"를
원자적으로 수행하는 기능이 없다. 읽고 → 판단하고 → 쓰는 사이에 다른 요청이
끼어들 수 있고, Vercel 은 요청마다 다른 인스턴스에서 실행되므로 코드로 락을
걸 수도 없다. `LockService.getScriptLock()` 은 구글이 제공하는 전역 뮤텍스라
별도 DB 없이 순서를 보장할 수 있는 유일한 수단이다.

**락 구간을 최소화한 이유.** 락 안에서 시트를 직접 읽고 쓰면 요청 하나당
0.5초씩 잡아먹어 80명이 몰리면 마지막 사람이 40초를 기다린다. 그래서 락
안에서는 `ScriptProperties` 의 점유 현황만 갱신하고(≈100ms), 시트에 이름을
쓰는 작업은 락을 푼 뒤에 한다. 승패는 락 안에서 이미 결정되므로 시트 반영이
수백 ms 늦어도 결과는 달라지지 않는다.

**Next.js 가 Apps Script 를 대신 호출하는 이유.** Apps Script 웹앱은 302
리다이렉트를 거치고 CORS 프리플라이트를 지원하지 않아 브라우저에서 직접
호출하기 번거롭다. 서버를 경유하면 그 문제가 사라지고, `GAS_URL` 과 토큰도
클라이언트에 노출되지 않는다.

## 배포

### 1. Apps Script

1. [script.google.com](https://script.google.com) → **새 프로젝트**
2. `apps-script/Code.gs` 내용을 붙여넣기
3. 좌측 **프로젝트 설정** → "`appsscript.json` 매니페스트 파일 표시" 체크 →
   `apps-script/appsscript.json` 내용으로 교체
4. 편집기에서 함수 `setupToken` 을 **1회 실행** → 권한 승인 →
   실행 로그에 찍힌 `GAS_TOKEN=…` 값을 복사해 둔다
5. **배포 → 새 배포 → 유형: 웹 앱**
   - 실행 계정: **나**
   - 액세스 권한: **모든 사용자**
   - 배포 후 나오는 `…/exec` 주소를 복사해 둔다

> 실행 계정이 "나"여야 학생이 구글 로그인 없이 신청할 수 있고, 스크립트가
> 소유자 권한으로 시트에 쓸 수 있다.

시트는 이 스크립트 소유자가 **편집 권한**을 가지고 있어야 한다. 학생에게는
시트 링크를 공유하지 않는다.

### 2. Vercel

1. 이 저장소를 Vercel 에 연결
2. 환경변수 4개 설정 (`.env.example` 참고)

   | 이름 | 값 |
   |---|---|
   | `GAS_URL` | 1단계에서 복사한 `…/exec` 주소 |
   | `GAS_TOKEN` | `setupToken()` 로그에 찍힌 값 |
   | `ADMIN_PASSWORD` | 관리자 페이지 비밀번호 |
   | `ADMIN_COOKIE_SECRET` | 아무 임의 문자열 (`openssl rand -hex 32`) |

3. 배포 후 `https://…vercel.app/admin` 에서 설정

로컬 개발은 `.env.example` 을 `.env.local` 로 복사해 값을 채운 뒤 `npm run dev`.

## 운영

`/admin` 에서 매 회차마다:

1. **시트 연결** — 구글시트 주소를 넣고 `시트 확인` → 탭 선택
2. **신청 받을 날짜** — 이번에 열 날짜를 체크 → `열릴 자리 확인` 으로 칸 수 검증
3. **오픈 시간** — 신청 시작 시각 지정 (마감은 비워두면 무제한)
4. **설정 저장**

시간 입력은 **관리자 브라우저의 시간대**를 기준으로 한다. 한국에서 설정하면
그대로 한국 시간이다.

### 신청 가능 칸을 정하는 규칙

체크한 날짜 열에서 **배경이 흰색인 칸**만 신청을 받는다. 회색·주황색 등
색이 칠해진 칸은 자동으로 제외된다. 즉 **지금까지 하던 대로 시트에 색을
칠해 두면 그대로 반영된다.**

이미 이름이 적혀 있는 흰색 칸은 신청 완료로 취급한다.

> **주의:** 배경색을 한 번도 지정한 적 없는 칸도 흰색으로 읽힌다. 아직 정리하지
> 않은 날짜 열을 체크하면 의도치 않게 열릴 수 있으니, 저장 전에 반드시
> `열릴 자리 확인` 으로 칸 수를 확인할 것.

### 도구

| 버튼 | 용도 |
|---|---|
| 시트 다시 읽기 | 시트에서 색을 바꾼 뒤 즉시 반영 (평소엔 5분마다 자동 갱신) |
| 시트에 다시 쓰기 | 신청 현황을 기준으로 시트를 맞춤. 시트 반영이 실패했을 때 복구용 |
| 시트에서 가져오기 | 시트를 직접 고쳤을 때, 시트를 정답으로 삼아 현황을 다시 만듦 |
| 신청 내역 전체 삭제 | 다음 회차 시작 전 초기화 |

시트를 직접 수정하는 습관이 있다면, 수정 후 **시트에서 가져오기**를 눌러
현황을 맞춰야 한다. 누르지 않으면 시트와 신청 현황이 어긋난다.

## 알아둘 점

- **동시 접속 시 대기.** 락이 요청을 한 줄로 세우므로 80명이 정각에 몰리면
  마지막 사람은 10초 내외를 기다린다. 순서와 결과는 보장되지만 즉답은 아니다.
- **1인 1자리.** `이름 + 연락처 뒤 4자리`를 같은 사람으로 본다. 다른 자리를
  원하면 기존 신청을 취소해야 한다.
- **자리가 모자란 경우는 해결하지 않는다.** 이 시스템은 선착순 판정만 고친다.
  신청 가능한 칸보다 인원이 많으면 남는 인원은 그대로 남는다. 대기열이
  필요하면 별도 기능으로 추가해야 한다.
- **시트에서 가져온 신청은 본인 취소가 불가능하다.** 연락처를 알 수 없어
  본인 확인을 할 수 없다. 관리자가 현황 표에서 삭제해야 한다.

## 구조

```
apps-script/
  Code.gs            락 + 선점 판정 + 시트 읽기/쓰기 (JSON API)
  appsscript.json    웹앱 배포 설정
src/
  app/
    page.tsx         신청 페이지
    admin/page.tsx   관리자 페이지
    api/
      state/         현황 조회 (전체 / 폴링용 경량)
      claim/         신청
      cancel/        취소
      admin/         로그인 + 관리자 동작 프록시
  components/
    SlotGrid.tsx     시간표 (데스크톱 격자 / 모바일 날짜탭)
  lib/
    gas.ts           Apps Script 호출
    auth.ts          관리자 세션
    types.ts
```
